# Delivery record: BYE schedule API and online key management

**Recorded:** October 19, 2026, Pacific time. Earlier schedule/database work is
included as context; online owner access was completed and verified on this date.

## What we set out to solve

BYE needed one dependable source of PCC schedule information that could serve
Windows, Mac and the website. Fetching PCC separately from each client would make
search slower, repeat work, and increase traffic to PCC. Keeping data retrieval
inside each app would also mean rebuilding clients to distribute many backend fixes.

We built a standalone API: a service that clients can ask for course and section
data. We then added shared application keys and a dashboard so the owner can
manage access without redeploying that service. The dashboard first ran locally;
it was then moved to its own hosted site so it could be used away from this computer.

## How the pieces work together

The schedule path is: **PCC → shared importer → Supabase → BYE API → future clients**.
A client read uses the last validated data in Supabase; it does not wait for a new
PCC download. Catalog and seat availability have separate versions, so a seat
change does not force a full catalog download.

The management path is: **owner sign-in → hosted dashboard → management API → private
key registry**. The registry decides which keys may read schedules. Changing a key's
status takes effect without an API deployment. The API checks the database even
when a caller asks to reuse a cached response.

The dashboard does not have to remain open for the schedule API or synchronization
to run. It is a management tool, rather than the service that supplies schedule data.

## Main decisions and why we made them

| Decision | Reason and practical consequence |
| --- | --- |
| Keep the API independent of client releases | Compatible backend fixes can ship without rebuilding every app. Clients will use a stable v1 contract; breaking changes need a new version. |
| Start with Fall 2026 only | A smaller pilot lets us validate the importer and data meaning before expanding semesters. The API never silently switches terms. |
| Preserve official course codes and source details | Leading zeros, CCN prefixes and full suffixes can identify different courses. Multiple meetings, dates and instructors must not be flattened away. |
| Keep PCC status separate from seat counts | A section can be closed while still showing seats. Unknown information stays unknown instead of being guessed. |
| Share PCC synchronization | A daily full check and activity-driven checks avoid one PCC poller per user. There is no more than one semester fetch per five minutes. |
| Show freshness honestly | Availability becomes stale after fifteen minutes without a successful check, and stale counts are suppressed. Five-minute collection is a target, not a guarantee of PCC's own update speed. |
| Use keys for applications, not students | A Windows key can be shared by many Windows installations. Thirty users do not require thirty manually managed keys. A public app key is identification, not proof of a genuine installation. |
| Retain only key fingerprints | The registry stores a SHA-256 digest, not recoverable plaintext. A new key is shown once and must be saved at creation. |
| Allow overlapping rotation | A replacement works immediately while the old key has a thirty-day transition period. Installed clients still need a separate way to receive that replacement. |
| Host a separate Cloudflare admin site | The owner needs access away from this computer. Cloudflare can serve the interface and server-side sign-in; GitHub Pages alone cannot run the current server-side session flow. |
| Keep login tokens in server memory | The browser receives an opaque secure cookie, not a Supabase access token. A server restart may require sign-in again, but does not lose keys or history. |
| Preserve existing review behavior | This phase does not change student-review records, IDs, professor profile choices, or RMP behavior. |

Cloudflare remained on the existing Free plan. The first deployment rejected a
custom CPU-limit setting because it required a paid plan; we removed that setting
and used the built-in Free limits. No paid upgrade was enabled.

## Key behavior in everyday terms

A normal key has no automatic expiry. App updates do not require new keys.

- **Create** makes a new shared application key and displays it once.
- **Rotate** creates an active replacement and schedules the old key to stop working
  thirty days later. It does not install that replacement into existing apps.
- **Extend retirement** postpones that deadline. An expired key requires an explicit
  confirmation before its eligibility is restored.
- **Disable / enable** temporarily blocks or restores a key, while still respecting
  any retirement date.
- **Revoke** permanently blocks a key and keeps its audit history for the retention period.

The existing accepted key was registered before switching access checks to the
registry. At the end of verification it remained active with no retirement date.
The old compiled-key fallback was removed, so it cannot bypass a revoked registry entry.

## What we learned during the owner walkthrough

The owner signed in and created, rotated, extended and revoked test keys. Two
findings affected the final dashboard:

1. The embedded browser does not support native `prompt()` calls. Retirement
   extension was changed to a form inside the page. Rotate and Revoke also use
   in-page confirmations, and all three show the selected key's name, mask and ID.
2. The original compatibility key was accidentally rotated during testing. Its
   no-expiry setting was restored through an audited owner-recovery action. The
   accidental replacement and both intended test keys were subsequently revoked.
   Replacement names now include “replacement” to make the rows easier to distinguish.

The owner then confirmed real sign-in on the hosted Cloudflare address and saw
the same key records. A final check confirmed the original key was still active,
and all three temporary keys were revoked.

## What is intentionally not finished

Windows, Mac and the public website still use their existing data flows. They do
not yet use this API or automatically receive replacement keys. The next phase
is client integration: use a local catalog, read the API on startup and Refresh,
and run one bounded sixty-second check while a client is visible and online.

Additional semesters, public website rollout, Windows folder naming, textbook
retrieval, undocumented PCC field meanings and broader operational observation
remain separate work. This milestone establishes the backend and its management
controls; it does not claim the whole app migration is complete.
